# Автоматизация Newsroom

Этот блок укрепляет автоматическое создание ролика и выпускает его без подтверждения человеком.
Расписания и обработчик доработок включаются отдельно от доставки кода.

## Что реализовано

- У каждой сборки собственные `run_id`, теги образов и контейнеры. Общего удаления чужих контейнеров больше нет.
  Таймер внутри контейнера останавливает работу даже после потери клиента; клиент тоже ограничивает Docker-команды.
- Кеш OpenRouter сохраняется в Docker volume между запусками. Запись кеша атомарная с отдельным временным файлом
  на каждый запрос. `STUDIO_IMAGE_CACHE_VOLUME` задаёт имя volume, по умолчанию `8bitnews-studio-image-cache-v1`.
- `STUDIO_COMMAND_TIMEOUT_S` — максимум времени одной Docker-команды/контейнера, по умолчанию 1800 секунд.
  `STUDIO_IMAGE_BUDGET_USD` — бюджет одного клиента генерации, по умолчанию $2. После достижения бюджета новые
  платные запросы блокируются, кеш читается. Последний запрос может превысить остаток: стоимость известна после ответа.
  Это не общий суточный бюджет всех агентов и всех пересборок.
- `release_submit` валидирует все пять JSON-контрактов, канал, связь сценария/Video/QA/Legal, технические проверки,
  разрешённые площадки, принадлежность медиа повороту, длину и SHA-256 загруженных видео, субтитров и обложки.
- Релиз и его источники создаются одной транзакцией. Идентичная повторная сдача возвращает тот же `release_id`;
  другой пакет для активного поворота получает конфликт. Проверенные источники повторно доступны из БД.
- Регистрация сюжета и поворота атомарна. Резервирование по каналу, времени события и каноническим seed URL
  защищает от повторной регистрации при изменении заголовка/UTM-параметров и одновременных запусках.
  `polymaths_task_id` резервирует исходную задачу за событием. Смысловые дубли с другими URL/временем по-прежнему
  проверяются через `story_find_similar` и редактором.
- `stage_report.py` извлекает результаты всех пяти команд из JSON. Research/Script получают `approved` только
  от ревью с `parent_id`, равным последнему итоговому артефакту. Summary для роутера формируется тем же кодом.
- При `changes_requested` причина модератора и задание на доработку записываются вместе. Повтор той же причины
  не создаёт вторую задачу. Обработчик хранит lease, попытки и ошибку в `rework_jobs`; после пяти неудач или
  постоянной ошибки API переводит задание в `needs_human`. Отсутствие исходного task_id тоже требует человека.
- Перед повторным POST feedback обработчик ищет свой стабильный маркер в истории замечаний исходной задачи.
  Это восстанавливает доставку после потери ответа. Обработчик не отменяет задачи и не создаёт новые сюжеты.

## Доставка и совместимость

1. Миграция `00006_automation.sql` добавляет резервирование событий, происхождение релиза и очередь доработок.
   Она применяется после миграции 00005 страницы расходов, уже включённой в общий релиз.
2. Новый hub требует `research_dossier_artifact_id`, `script_artifact_id` и `video_package_artifact_id` при сдаче. Обновлённый `release_submit.py`
   передаёт их и исходный task_id из метаданных `story_brief`. Новую версию hub и инструментов сдачи нужно
   доставлять согласованно; существующие релизы остаются читаемыми.
3. Обновить конфигурацию Newsroom обычным `python3 newsroom/sync.py newsroom` после доставки исходников.
   Здесь обновляются producer, router и editor. Инструкции запрещают дорогой прогон без доступного hub.
4. Для обработки доработок задать `HUB_POLYMATHS_WRITE_API_KEY`; адрес по умолчанию —
   `HUB_POLYMATHS_URL=https://polymaths.work/api/v1`. Пока ключ не задан, задания остаются в БД.
   Это отдельный ключ записи; `HUB_POLYMATHS_API_KEY` остаётся ключом только для чтения страницы расходов.
   Значения поддержаны в env, Compose и Ansible. Секреты в репозиторий не записываются.

## Публикация без подтверждения

Решение владельца 09.11.2026: «ролик готов и сразу ты загружаешь с расписанием». Включается в профиле канала:
`moderation.approval_required: false`. Канал без этого явного `false` по-прежнему ждёт человека.

Маршруты `/api/v1/publishing/*` открывает только `HUB_PUBLISHER_API_KEY`: агенты конвейера читают чужие страницы и держат
другой ключ. Без этого значения маршруты закрыты.

1. Карточка уходит в группу как обычно. Сразу после неё hub одобряет релиз от имени `auto`, и открывается страница
   источников. Перезапуск между карточкой и одобрением релиз не теряет. Карточка старше 48 часов остаётся за человеком:
   новость устарела, а одобрение вручную идёт прежним путём, с пакетом для загрузки.
2. Релиз появляется в `GET /api/v1/publishing/queue` → `upload`: пакет YouTube и `publish_notes` Legal. В очередь попадают
   только автоматически одобренные: ролик, одобренный вручную, мог быть выложен без записанной ссылки. Если у пункта уже есть
   `publish_at`, прошлая попытка могла дойти до YouTube: сначала посмотреть в Studio.
3. Загрузчик берёт слот `POST /api/v1/publishing/releases/{id}/slot`: не раньше чем через 45 минут; день за днём, внутри дня
   в порядке `schedule.publish_slots` (первый — основной). Один слот на один ролик канала. Релиз держит свой час, пока этот час не
   пройдёт или не будет `DELETE /youtube`, даже если его закрыли: это единственный след загрузки, ссылка которой не дошла.
   Задержанный релиз получает 409. Если свободный слот позже 72 часов со сдачи, тоже 409, и релиз задерживается: такой ролик
   сам не выходит.
4. Загрузчик ставит ролик в расписание YouTube на этот час и пишет `PUT /api/v1/publishing/releases/{id}/youtube`
   `{"video_id": "…", "publish_at": "…"}`.
5. После слота hub раз в 2 минуты смотрит oEmbed (он не отличает Public от Unlisted). Ролик виден — релиз `published`, он в
   списке канала, в группе «🟢 Вышел». Ссылка без записанного слота проверяется так же, но молча.

**Когда hub пишет в группу.** Каждый случай один раз на ролик: ролик задержан и почему; не загружен за 6 часов после
одобрения (загрузчик не работает); не вышел через 30 минут после слота; вышел, хотя релиз закрыт или задержан.

**Остановить.** «🚫 Закрыть страницу источников» закрывает релиз. Если ролик уже в расписании, он попадает в
`queue` → `unschedule`: загрузчик снимает его с расписания и вызывает `DELETE /api/v1/publishing/releases/{id}/youtube`.
Пустой `url` значит, что слот взят, а ссылки нет: надо посмотреть в Studio. На автоматических карточках нет «🟢»: отметка до
выхода показала бы ролик в списке канала раньше времени.
Пока загрузчик не работает, снимать надо в Studio самому. Доработки с карточки нет: кнопка «Доработать» только до одобрения.

**Условия Legal.** Пункт `publish_notes`, начатый со `СТОП:`, загрузчик проверяет перед загрузкой. Условие сработало —
`POST /api/v1/publishing/releases/{id}/hold` `{"reason": "…"}`, группе напишет hub; `DELETE` того же адреса возвращает ролик
в очередь. Остальные пункты он выполняет сам. Ролик, который нельзя выпускать по условию самого Legal, не считается готовым.
Между загрузкой и слотом условие никто не перепроверяет.

**Кто загружает.** Пока Claude Code через браузер: это работает, только когда открыта его сессия. Условия YouTube запрещают
автоматический доступ к сервису без письменного разрешения (`platforms/youtube/rules.md`), так что это временно. Следующий шаг —
загрузка из hub через YouTube Data API.

**Что изменилось для зрителя и для права.** Страница источников ролика без одобрения говорит, что человек его не смотрел.
В описании AI-текст раскрыт явно: исключением human review из ст. 50(4) AI Act больше не пользуемся
(`operator/legal.md#ai-act-our-case`). При включении надо заменить текст «О канале» на обоих каналах: там сказано, что человек
одобряет каждый ролик.

## Расписания и наблюдение

Показать локальный план без сетевых запросов и создания задач:

```sh
python3 newsroom/automation.py schedules
```

Создать отсутствующие расписания в PolyMaths из `schedule.runs` и часового пояса каждого канала:

```sh
python3 newsroom/automation.py schedules --apply
```

Ключ берётся из `POLYMATHS_API_KEY` либо локального `.mcp.json`, как у `sync.py`.
Управляемые имена — `8bitnews/<channel_id>/<номер>`, команда — Newsroom, намерение — `explanation`.
Повтор с совпадающими настройками ничего не создаёт. Дубли имён, неполный список или несовпадение существующего
расписания останавливают применение; существующие расписания скрипт не удаляет и не перенастраивает.
Применение выполняется одним оператором, без параллельных запусков команды создания.

Проверить последние задачи или определённый запуск только на чтение:

```sh
python3 newsroom/automation.py status
python3 newsroom/automation.py status --task-id <uuid> --stale-minutes 30
```

Отчёт содержит статус, виды артефактов, наличие `release_receipt` и время без новых артефактов.
`active` без артефактов не считается результатом. Код выхода 1 означает зависание, `failed` или `needs_human`.
Наличие квитанции означает готовность к модерации, а не публикацию. Команда не перезапускает и не отменяет задачи.

Очередь доработок диагностируется в Postgres:

```sql
SELECT id, release_id, task_id, status, attempts, last_error, updated_at
FROM rework_jobs ORDER BY created_at DESC;
```

## Проверки

```sh
scripts/test-integration.sh
python3 -m pytest -q newsroom/tests
```

Интеграционный скрипт создаёт отдельный Compose project со случайными loopback-портами, временной Postgres
и собственным S3, создаёт тестовый bucket и удаляет только своё окружение при выходе.
`HUB_TEST_REQUIRE_SERVICES=true` делает ошибки инфраструктуры/миграций падением теста вместо пропуска.
CI запускает его и быстрые проверки Studio без моделей TTS, платной генерации и длительных рендеров.

## Что остаётся следующим этапом

Загрузка из hub через YouTube Data API с OAuth вместо браузера: ей нужен проект Google Cloud и согласие владельца
по каждому каналу (`platforms/youtube/setup.md`, раздел 4). Для неё же пункты `publish_notes` придётся разбирать
автоматически. Также остаются общая очередь кандидатов новостей, суточные лимиты всех агентов и подтверждённая
серия выпусков без ручного сопровождения.
